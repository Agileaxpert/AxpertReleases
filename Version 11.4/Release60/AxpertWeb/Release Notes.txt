TSK-0894 -- Enhancement: Dropdown Value Caching Using IndexedDB
As part of the product performance improvement initiative, dropdown field values will now be stored locally in the browser using 'IndexedDB'. This enhancement helps improve performance by reducing repeated database requests when retrieving dropdown values.
Important Notes:
1. Refresh on Save: For fields configured with `MOE` as the select option, avoid enabling the 'Refresh on Save' property unless it is required by the business logic. This helps maximize the performance benefits of local caching.
2. Refresh Button: Use the 'Refresh' button whenever the latest dropdown values need to be retrieved from the database.
Recommendation: Configure the 'Refresh on Save' property only when necessary, and use the 'Refresh' button when updated database values are required.
Note: After applying this patch, all existing in-memory cache keys must be cleared to ensure the updated caching mechanism works correctly.

TSK-0895 -- Enhancement: ADS-Level PageSize Configuration
The ADS definition has been enhanced to support configuring the PageSize for individual ADS definitions.
Changes:
1. Previous Behavior: If the ADS payload did not contain the 'PageSize' parameter, the product-level default value of '100' was used.
2. New Configuration Field: A new field, 'Pagesize for API', has been added to the ADS definition with the following dropdown values:25, 50, 100, 500, 1000, 5000
3. Updated Behavior:
   a. If the ADS payload contains 'PageSize', the value specified in the payload will be used.
   b. If the ADS payload does not contain 'PageSize', the value configured in the 'Pagesize for API' field of the respective ADS definition will be used.
Note: The payload-level 'PageSize' takes precedence over the ADS definition-level configuration. If the payload does not specify 'PageSize', the configured ADS-level value will be used instead of the previous product-level default of '100'.

TKT-1238 -- Enhancement: To prevent direct loading of HTML Pages
Configuration: Add the following configuration under the <system.webServer> section in the application's Web.config file.
  <modules runAllManagedModulesForAllRequests="true">
    <add name="AxpertHtmlAuth" type="AxpertHtmlAuthModule" />
  </modules>

Note:
1. Applicable `.html` and `.htm` pages require a valid login. 
2. `AppSettings.json` is optional and is not required by default. Create it in the application root only when specific HTML files need to bypass authentication.
3. Add bypass filenames to the `HtmlAuthBypassFiles` JSON array, for example:
   ```
   {
     "HtmlAuthBypassFiles": [
       "healthcheck.html",
       "CustomHtmlPage.html"
     ]
   }
   ```
4. Add each listed file to the site folder if it is not already present.
5. Use filenames only. Entries containing `/`, `\`, or `:` are ignored.
6. If the file is missing, unreadable, malformed, or has no valid filename array, no bypass files are configured; normal authentication handling continues.
7. Bypassed files are served without login. Only add static pages with no sensitive content, and only at the Environment or Network team’s request or custom pages if required.
8. The list is read when the application starts. Recycle the application pool after changing it.
Example: The AxpertWeb code folder contains `healthcheck.html` on the alpha.axi server, but that file is not released with the product. To allow it on that server, create `AppSettings.json` in the deployed application root and include `"healthcheck.html"` in `HtmlAuthBypassFiles`.
